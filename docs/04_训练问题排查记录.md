## 2. CIFAR10 自回归训练

### 2.1 初始目标

CIFAR10 自回归任务把图片展平成 byte 序列：

```text
image shape = [3, 32, 32]
sequence length = 3 * 32 * 32 = 3072
seq_len = 3071
```

训练目标：

```text
x = sequences[:, :seq_len]
y = sequences[:, 1:seq_len + 1]
```

目标论文近似配置：

```text
seq_len = 3071
AFT-local-256
n_layers = 24
d_model = 256
hidden_dim = 1024
```

### 2.2 问题一：AMP 下 causal mask 使用 -1e9 导致 overflow

现象：

```text
RuntimeError: value cannot be converted to type at::Half without overflow
```

触发位置：

```text
src/aft/layers.py
bias = bias.masked_fill(~causal_mask, -1e9)
```

原因：

```text
AMP 开启后，部分张量会变成 float16。
float16 不能表示 -1e9 这么大的负数。
```

解决：

```text
把 -1e9 改成 -1e4。
```

原因是：

```text
exp(-1e4) 已经接近 0，足够屏蔽未来位置。
-1e4 又不会在 float16 中溢出。
```

结论：

```text
该问题解决后，AMP 下 causal mask 不再报 overflow。
```

### 2.3 问题二：dense AFT-local 在 CIFAR10 长序列上 OOM

初始 AFT-local 直接构造：

```python
k = k.unsqueeze(1)                       # [B, 1, T, D]
v = v.unsqueeze(1)                       # [B, 1, T, D]
bias = bias.unsqueeze(0).unsqueeze(-1)   # [1, T, T, 1]
scores = k + bias                        # [B, T, T, D]
```

完整 CIFAR10 配置：

```text
B = 1
T = 3071
D = 256
```

`scores` 元素数：

```text
1 * 3071 * 3071 * 256 ≈ 2.4 billion
```

现象：

```text
torch.OutOfMemoryError: CUDA out of memory
Tried to allocate 9.00 GiB
```

判断：

```text
dense 直接计算版本虽然公式最直观，但 [B, T, T, D] 对 CIFAR10 长序列不可接受。
```

解决方向：

```text
不能继续使用 dense 版本跑完整 seq_len=3071。
必须改成更省显存的 causal AFT-local 实现。
```

### 2.4 问题三：offset 省显存版能跑但极慢

为避免 `[B, T, T, D]`，使用代数分解：

```text
exp(k_s + w_{t,s})
= exp(k_s) * exp(w_{t,s})
= exp(k_s) + exp(k_s) * (exp(w_{t,s}) - 1)
```

先用 `cumsum` 算全局历史项：

```python
global_numerator = kv.cumsum(dim=1)
global_denominator = exp_k.cumsum(dim=1)
```

再按 offset 补局部修正：

```text
offset = t - s
offset = 0, 1, ..., local_window_size
```

优点：

```text
显存明显下降。
不再构造 [B, T, T, D]。
```

缺点：

```text
local_window_size = 256 时，每层循环 257 次。
n_layers = 24 时，每个 micro batch 大约 257 * 24 = 6168 次 Python offset 循环。
```

结论：

```text
offset 版本数学正确，但训练速度太慢，不适合作为正式长训实现。
```

### 2.5 问题四：chunked gather 版本能吃满 GPU，但完整 24 层配置仍太慢

进一步把 offset 循环改成 chunked gather：

```text
按目标位置分块。
一次取 C 个 target position。
每个 target position 取 K = local_window_size + 1 个 source position。
```

核心形状：

```text
source_positions: [C, K]
kv_source:        [B, C, K, D]
expk_source:      [B, C, K, D]
bias:             [C, K]
correction:       [1, C, K, 1]
```

局部修正：

```python
local_numerator[:, start:end, :] = (correction * kv_source).sum(dim=2)
local_denominator[:, start:end, :] = (correction * expk_source).sum(dim=2)
```

实测完整配置：

```text
seq_len = 3071
n_layers = 24
local_window_size = 256
grad_accum_steps = 64
use_checkpoint = True
GPU = 2 * RTX 5090
```

现象：

```text
GPU 利用率: 100%
显存占用: 约 3.5GB/GPU
运行约 12 小时仍未到 step 500
```

判断：

```text
不是卡死，GPU 确实在计算。
但 step 500 = 500 * 64 = 32000 个 micro batch。
每个 micro batch 又有 T=3071、24 层、window=256。
use_checkpoint=True 会在 backward 时重算 forward，进一步拖慢。
```

结论：

```text
chunked gather 是当前必须使用的长序列实现。
但完整 24 层 + window256 + accum64 + checkpoint 配置在 2 * RTX 5090 上训练成本过高。
```

### 2.6 问题五：回退 dense 版本验证速度，结果 OOM

曾尝试回到 dense 直接计算版，以验证是否“GPU 大矩阵一次算完会更快”。

结果：

```text
seq_len=3071, n_layers=24, window256
backward 阶段 OOM
Tried to allocate 9.00 GiB
```

结论：

```text
dense 版本不适合完整 CIFAR10。
不能用它解决速度问题。
```

### 2.7 问题六：AdamW 参数分组回退尝试

曾短暂把 AdamW 从参数分组：

```python
param_groups = build_weight_decay_param_groups(model, weight_decay)
optimizer = torch.optim.AdamW(param_groups, lr=learning_rate)
```

回退成：

```python
optimizer = torch.optim.AdamW(
    model.parameters(),
    lr=learning_rate,
    weight_decay=weight_decay,
)
```

目的：

```text
排查训练速度和 OOM 是否与 AdamW 参数分组有关。
```

结果：

```text
OOM 和训练慢主要来自 AFT-local 中间张量与训练配置。
与 AdamW 参数分组无直接关系。
```

最终恢复：

```text
普通权重使用 weight_decay。
bias / LayerNorm / position 参数不使用 weight_decay。
```

### 2.8 问题七：没有到 save_interval，重新运行会从头开始

现象：

```text
训练跑到 step 400 左右后中断。
重新执行命令时从 step 0 开始。
```

原因：

```text
save_interval = 500
只有到 step 500 才会保存 model checkpoint。
step 400 时还没有 .pt checkpoint。
```

注意：

```text
--use-checkpoint 是 activation checkpointing，只影响省显存和 backward 重算。
它和保存/恢复训练无关。

--output-path 才是 model checkpoint 保存路径。
只有 output_path 文件存在时，训练脚本才会 resume。
```

解决：

```text
如果希望更频繁恢复，可以把 --save-interval 改小，例如 100。
当前为了减少 IO，CIFAR10 reduced setting 使用 save_interval=500。
```

### 3.4 batch-size 512 + lr 3e-4 + AMP 导致 NaN

为了提高 GPU 利用率，尝试：

```text
batch_size = 512 per GPU
effective_batch_size = 1024
learning_rate = 3e-4
amp = True
```

现象：

```text
train loss: nan
val loss: nan
top1: 0.1
top5: 0.5
```

判断：

```text
top1=0.1%、top5=0.5% 基本是 1000 类随机猜水平。
loss=nan 说明模型参数或中间计算已经数值炸掉。
```

原因：

```text
AFTConv2D 中直接计算 exp(k)。
ImageNet + AMP float16 下，k 稍大就可能 exp(k) 溢出成 inf。
后续 inf / inf 会变成 nan。
batch 512 和 lr 3e-4 对当前实现过于激进。
```

### 3.5 坏 checkpoint 被自动 resume

现象：

```text
换成 batch_size=128, lr=1e-4 后仍然立刻出现 nan。
日志显示 start epoch: 5。
```

原因：

```text
脚本发现 output_path 已存在，自动加载 checkpoint。
该 checkpoint 已经来自 NaN 模型。
一旦模型参数中有 NaN，继续 resume 仍然会 NaN。
```

解决：

```text
不要 resume 坏 checkpoint。
换新的 output_path/log_path，或把旧 checkpoint 改名为 *_nan.pt。
```

判断标准：

```text
干净训练应该显示 start epoch: 0。
如果显示 start epoch > 0，说明正在 resume。
```

### 3.7 修复 AFTConv2D 的 exp(k) 数值稳定

原始代码：

```python
exp_k = torch.exp(k)
kv = exp_k * v
```

问题：

```text
AMP 下 k 可能是 float16。
float16 最大有限，exp(k) 很容易变成 inf。
```

修复：

```python
k_float = k.float()
v_float = v.float()
k_float = k_float - k_float.amax(dim=1, keepdim=True)
exp_k = torch.exp(k_float)
kv = exp_k * v_float
```

门控输出也改为：

```python
y = torch.sigmoid(q.float()) * numerator / (denominator + 1e-6)
y = y.to(q.dtype)
```

为什么这样不改变公式：

```text
对同一个 batch、同一个通道，所有 patch/token 的 k 同时减去同一个最大值 m。
加权平均中分子和分母都会乘以 exp(-m)。
这个公共因子会相互抵消。
因此 exp(k_s - m) / sum_s exp(k_s - m) 与原始比例等价。
```

验证：

```text
pytest: 23 passed
AFTImageClassifier forward/backward: 通过
```

### 3.10 学习率计算误解

曾误以为学习率是类似 `x^2` 的曲线。

实际代码使用：

```text
前 warmup_epochs 个 epoch: 线性 warmup
warmup 结束后: cosine decay
```

当前配置：

```text
learning_rate = 1e-4
min_learning_rate = 1e-5
warmup_epochs = 5
epochs = 90
```

warmup 阶段：

```text
epoch 0: 1e-4 * (0+1)/5 = 2e-5
epoch 1: 1e-4 * (1+1)/5 = 4e-5
epoch 2: 1e-4 * (2+1)/5 = 6e-5
epoch 3: 1e-4 * (3+1)/5 = 8e-5
epoch 4: 1e-4 * (4+1)/5 = 1e-4
```

cosine 起点：

```text
epoch 5: cos(0)=1，所以仍是 1e-4
```

之后平滑下降：

```text
epoch 6: 9.9969e-5
epoch 7: 9.9877e-5
```

结论：

```text
学习率不是跌宕起伏，而是先线性上升，再平滑下降。
训练指标的波动不等于学习率波动。
```
